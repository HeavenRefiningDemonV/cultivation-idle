# Section A — Global Doctrine and Source Hierarchy

This document is the canonical **Section A** doctrine charter for the UI overhaul. In this project, **Section A means the future Codex split for global doctrine and merge rules, not Appendix A**. Future UI packets must cite this file as the operational source of truth so work does not re-interpret the full constitution on every pass.

## Purpose and interpretation

Section A exists to lock global decision law before any packet-level implementation. This file defines what controls layout, atmosphere, practical feasibility, and mechanic correctness when sources disagree. It also defines what cannot be violated by later packets, regardless of local taste or visual preference.

Section A is not optional guidance. It is enforceable doctrine. Future packets must treat every law in this file as hard constraints, not suggestions.

## Source hierarchy (authoritative order)

| Source family | What it controls | Override rule |
| --- | --- | --- |
| UI redesign master brief | Layout structure, information architecture, macro composition, clarity-first arrangement of modules | Must be treated as the layout authority. If any visual idea conflicts with this layout authority, the idea must be adjusted or rejected. |
| Uploaded mockups | Atmosphere, tone, mood, stylistic depth, ornamental direction, finish quality targets | Must be treated as atmosphere authority only. Atmosphere may enrich the build only when it does not violate layout authority, gameplay truth, or practical repo constraints. |
| Current repo foundation and current asset base | Practical implementation reality, ownership boundaries, reusable systems, existing scenic layers, available production assets | Must be treated as practical authority. Existing ownership must be reused and enhanced when functional; reinvention is invalid when there is no functional gain. |
| Current gameplay truth | Mechanics, readiness states, module roles, prestige meaning, progress semantics, interaction truth | Is the final override across all sources. If ornament, mockup style, or layout preference implies wrong gameplay meaning, gameplay truth always wins. |

### Operational override rules

1. **Gameplay truth always beats ornament.** Any ornamental choice that implies incorrect mechanic, status, readiness, role, or prestige meaning must be rejected.
2. **Layout clarity always beats beauty when they conflict.** A clearer layout is always correct over a prettier but less readable arrangement.
3. **Existing repo ownership beats reinvention when rewrite has no functional gain.** Replacement for novelty is invalid.
4. **Mockup atmosphere may push quality deeper only inside constraints.** It may not violate gameplay truth, layout truth, or practical feasibility.

## Executive thesis

The overhaul is **additive, not destructive**. The current build is the substrate, not the enemy. The goal is to preserve each screen’s strong existing identity and wrap it with stronger chrome, readability, layering discipline, and restrained FX where those improvements increase legibility and perceived quality.

This doctrine does not authorize a remake. It authorizes a disciplined enhancement pass that keeps valid structure, deepens presentation, and corrects weakness without erasing functional ownership. Existing scenic ownership must be preserved when it already carries fantasy, structure, or readability value.

## Non-negotiable laws (canonical labels)

The following labels are canonical terms. Future packets must use these exact labels and keep their meaning intact.

1. **Preserve-first** — If an existing screen element already carries fantasy, structure, or readability value, the packet must preserve it as the baseline rather than replacing it.
2. **Enhance-first** — If an existing asset or layer is useful but underpowered, the packet must upgrade, tune, and reinforce it before replacement is considered.
3. **New-art-last** — New art must be created for missing support roles first, never as the default first answer when current assets can be enhanced.
4. **Current-build-is-truth** — The live build is the implementation substrate; packets must evolve it directly and must not treat it as disposable scaffolding.
5. **Four-layer model** — Work must respect the ordered stack: gameplay truth (mechanic meaning), layout truth (information structure), scenic ownership (existing visual identity), and polish layer (atmosphere/FX); upper layers must not break lower layers.
6. **No cutover without completion** — No old art layer or incumbent presentation layer may be removed until the enhanced replacement is fully visible, wired, stable, and approved on that exact screen.
7. **Hero vs dense split** — Hero zones may carry richer atmospheric treatment, but dense utility zones must prioritize compact readability and interaction clarity over decorative weight.
8. **No layout shift** — Enhancement must not introduce disruptive structural movement; the screen must remain spatially stable during interaction and state transitions unless movement is a deliberate gameplay signal.
9. **No future-art excuse** — A packet must not leave a screen temporarily ugly, broken, or incoherent on the promise that future art, FX, or later polish will fix it.
10. **Code-first sequencing** — Implementation sequencing must lock functionality and truthful states first, then apply presentational enhancement inside that truthful base.

## Additive doctrine details

- This overhaul is not a remake and must never be executed as destructive replacement.
- Existing scenic ownership must be retained where it communicates world fantasy, module identity, or legibility.
- Current assets must be used and enhanced first before generating support art.
- New support art is valid only for true gaps where current assets have no usable role.
- Replacement is valid only when enhancement cannot meet gameplay truth, layout clarity, or practical reliability.
- No transition step may degrade a production screen below its pre-packet functional readability.

## Merge decision protocol when sources disagree

When conflicts occur, packets must resolve them in this order:

1. Validate mechanic meaning against current gameplay truth.
2. Validate information structure against layout authority from the redesign master brief.
3. Validate feasibility and ownership against current repo foundation and current asset base.
4. Apply atmosphere guidance from uploaded mockups only after steps 1–3 pass.

If any step fails, the packet must revise or reject the conflicting choice. Prettier local outcomes do not justify source violation.

## What Section A governs

Section A governs the global doctrine layer for all future UI packets, specifically:

- Source hierarchy and precedence rules.
- Merge decisions when source families disagree.
- Preserve-first / enhance-first / create-later law via Preserve-first, Enhance-first, and New-art-last.
- Global cutover law through No cutover without completion.
- Packet inheritance doctrine: every packet inherits this section before applying local screen goals.

Section A is therefore the gatekeeper for cross-packet consistency, non-destructive sequencing, and truthful presentation.

## What Section A does not govern

Section A does **not** implement or decide the following:

- Renderer stack or package/tooling choices.
- Shared shell component architecture or technical composition.
- Screen-by-screen component implementation details.
- Art generation pipelines or production schedules.
- Numeric tuning values.
- Gameplay or economy balance changes.

Those concerns belong to later sections and packet scopes. Section A only defines doctrine constraints that those later scopes must obey.

## Packet inheritance and enforcement rule

All future UI packets must cite this doctrine before proposing local decisions. No future packet may contradict the source hierarchy, non-negotiable laws, additive thesis, or cutover law defined here.

If a future packet conflicts with this doctrine, the packet is wrong even if its local screen outcome appears prettier. Doctrine compliance is mandatory and precedes aesthetic preference.

## Explicit anti-drift guardrails

- Current gameplay truth always wins over purely ornamental visual choices.
- No cutover can occur before completion and approval on the exact target screen.
- Current assets must be used first before generating support art.
- A screen must never be made temporarily ugly on the assumption that future art or FX will repair it.

Technical renderer/shared-shell implementation belongs to later sections, not Section A.
